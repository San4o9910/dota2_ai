# NARMA: собственный сервис покадрового видеоанализа

Новый модуль использует PostgreSQL, FFmpeg/ffprobe, Pillow и Gemini API. OpenDota в нём не участвует. API сохраняет видео, PostgreSQL хранит очередь и результаты, отдельный процесс передаёт **каждый декодированный кадр** в Gemini небольшими упорядоченными группами. Аудио не отправляется, транскрибации нет.

Это реализация модуля, а не подтверждение запуска сервера или качества тренера. Реальный Gemini-прогон требует ключа, выбранной модели и проверки на размеченных Dota-видео. Автоматического рендера `.dem` в видео здесь нет: для него нужен совместимый клиент Dota. Независимый прототип чтения событий `.dem` находится в `../replay`.

## Запуск на отдельном сервере

1. Установить Docker с Compose. Скопировать `.env.example` в `.env` и заполнить секреты. `DATABASE_URL` должен указывать на обычный PostgreSQL. В данном Compose его имя хоста — `db`. Спецсимволы пароля в URL нужно кодировать.
2. Выбрать доступную проекту Gemini модель с поддержкой изображений и структурированного вывода; записать её точное имя в `GEMINI_MODEL`. Ключ нужен только worker, не браузеру и не серверу приёма видео.
3. Выполнить `docker compose up --build -d db migrate api`. Миграции выполняются до API. Проверить `/livez` и `/readyz` через локальный порт 8080. После ограниченного теста Gemini и настройки общего бюджета явно запустить worker: `docker compose --profile analysis up -d worker`. Сам профиль не останавливает worker, который уже запущен; для паузы использовать `docker compose --profile analysis stop worker`. PostgreSQL не публикуется наружу. API слушает только `127.0.0.1:8080` хоста.
4. Настроить HTTPS reverse proxy на отдельном домене перед `127.0.0.1:8080`. Лимит тела запроса минимум 6 МиБ, потоковая выдача видео с Range, без публичного кэша. Токен сервиса не должен попадать в access logs. Ограничить входящий трафик и число запросов на прокси.
5. На сервере сайта задать `VIDEO_SERVICE_ORIGIN=https://video.example.com` и тот же `VIDEO_SERVICE_TOKEN`. Сайт сам подставляет ID вошедшего аккаунта и закреплённый ник. Пользователь не может передать свой owner/account ID через веб-форму.
6. Проверить короткий собственный клип: загрузка → очередь → ненулевое число обработанных кадров → вывод с рабочим таймкодом → удаление. Затем провести разметку и проверку качества на Dota-клипах перед включением платных разборов.

Пример reverse proxy Caddy: `video.example.com { reverse_proxy 127.0.0.1:8080 }`. Настройте собственный домен и HTTPS; пример не включает настройку DNS и правила доступа. Токен сервиса — внутреннее доверие между сайтом и API, а не пользовательская авторизация. При переносе всего сайта сохраните проверку владельца и замените привязанный к Sites вход своим серверным входом.

## Бюджет и точность

- По умолчанию разрешено 3 600 кадров на файл, 250 попыток обращения к модели на задание и 1 000 на владельца за сутки. Для полного матча лимит кадров нужно осознанно поднять после измерения расходов: час при 60 fps — 216 000 изображений. Лимиты не выражены в долларах и не заменяют квоты проекта Google.
- Файл сверх лимита кадров отвергается целиком до обращения к модели. При исчерпании запросов сохраняются частичные результаты; полный разбор не заявляется.
- Перед каждым вызовом резервируется запись в БД, поэтому сбой и повторный запрос тоже расходуют бюджет. При неопределённом сетевом исходе запрос может быть оплачен повторно; exactly-once внешнего API не обещается.
- Сохраняются ID кадра, исходные PTS и time base, время относительно начала видеопотока и SHA-256 JPEG, переданного модели. Разрешение сохраняется, JPEG quality 94. Фильтрации кадров и изменения fps нет. Повторяющиеся PTS сохраняются с разными frame IDs.
- Завершение возможно только при непрерывном покрытии всех кадров. Ответ модели должен перечислить точные ID переданной группы; ссылки на отсутствующие кадры отклоняются. Это проверка доставки и формата ответа, а не доказательство правильного понимания изображения.
- Модель и версия схемы закрепляются на первом запуске. Нельзя продолжить старый результат другой моделью незаметно.
- В произвольном видео нет проверенного Steam ID: `identity_status=nickname_only`. Ник берётся из закреплённого профиля, но совпадение человека по видео не доказано. Для строгого ограничения «один реальный игрок» требуется связанный реплей с проверенными player slots и привязкой видеоперспективы. UI сообщает это ограничение. Не включать оплату как за подтверждённый персональный анализ до реализации такой связи.

## Хранение и восстановление

В PostgreSQL: владельцы заданий, снимок привязки игрока, прогресс, leases, журнал кадров, результаты и резервирование запросов. Видео находятся в приватном volume `media`, не в колонке bytea. API и worker должны видеть один volume. Для нескольких серверов потребуется отдельный адаптер приватного объектного хранилища; текущая реализация не является S3-адаптером.

Очередь использует транзакции и `FOR UPDATE SKIP LOCKED`. После истечения lease задание доступно другому worker; уже сохранённые группы повторно не отправляются. Максимум три попытки. Временный heartbeat показывает живой процесс, но не подтверждает работоспособность Google API. Удаление закрывает доступ и отзывает lease; занятое место учитывается до успешного удаления файлов. Worker повторяет неудавшееся удаление. Запрос к Gemini, уже ушедший до удаления, нельзя отозвать локально.

Загрузка возобновляется при повторном нажатии в той же открытой странице. После перезагрузки страницы автоматическое продолжение выбора локального файла ещё не реализовано. Политика очистки брошенных загрузок, автоматические резервные копии, метрики/оповещения и адаптер удаления всех материалов вместе с аккаунтом требуют настройки перед публичным запуском.

## Переход на RDS PostgreSQL

Формат SQL остаётся PostgreSQL. Нужны перенос данных через `pg_dump`/`pg_restore` или управляемую миграцию, проверка восстановления, окно переключения записи и новый `DATABASE_URL`.

Для RDS задайте `sslmode=verify-full&sslrootcert=/run/certs/rds-ca.pem`, смонтируйте актуальный AWS CA bundle read-only, разрешите доступ только от сервера приложения, включите резервные копии и PITR. Учетная запись приложения не должна быть владельцем других баз. Зафиксируйте совместимую версию PostgreSQL и проверьте миграции на ней. RDS не переносит видео: volume нужно отдельно сохранить/перенести или реализовать S3.

**Текущие аккаунты и старые разборы сайта ещё используют D1 и Sites-auth.** В PostgreSQL реализован новый видеомодуль. Полный перенос сайта на отдельный сервер требует отдельной миграции этих данных и авторизации; одной смены DATABASE_URL для всего приложения недостаточно.

## Проверки разработчика

`python -m pip install -r requirements.txt pytest httpx` и `PYTHONPATH=. pytest tests` проверяют декодирование, PTS, покрытие кадров и поддельный ответ модели без обращения к Google. Для SQL/API-проверки дополнительно задайте отдельную пустую `TEST_DATABASE_URL` PostgreSQL: тесты создают и очищают только таблицы видеомодуля. Никогда не используйте production DSN для тестов.

Первичная локальная SQL-проверка выполнена на PostgreSQL 18.3 через PGlite, а не на RDS. Это не проверка реальной конкурентности, TLS, Docker image build или эксплуатации. Для запуска требуются отдельные интеграционные проверки на выбранном PostgreSQL сервере.
